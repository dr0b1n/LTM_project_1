RAG-Powered Vendor Compliance Auditor

============================================================
2. PROJECT SUMMARY
============================================================

The RAG-Powered Vendor Compliance Auditor is a privacy-focused Third-Party Risk Management application. It analyzes vendor Master Services Agreements (MSAs), Service Level Agreements (SLAs), and similar contracts against internal enterprise IT security, data privacy, and operational governance policies.

The system must identify compliant, non-compliant, ambiguous, and missing contractual commitments. Every finding must be supported by retrieved contract evidence, including the relevant clause and page number where available. The application must generate structured audit findings and remediation recommendations without relying on unsupported model claims.

The solution is local-first to reduce exposure of confidential contract data. Sensitive information is redacted before embedding or LLM processing.

DEMO SCOPE NOTE: Implement only the smallest end-to-end subset needed to demonstrate the technologies. The detailed production controls in this file are future-work references, not current implementation requirements.

============================================================
3. PROBLEM STATEMENT
============================================================

Manual contract review is slow, repetitive, inconsistent, and prone to missed risks. Vendor agreements may fail to meet internal requirements for encryption, breach notification, audit rights, data retention, data deletion, subcontractor controls, business continuity, availability, and other obligations. Confidential contract information must also be protected during AI processing.

============================================================
4. PROJECT OBJECTIVES
============================================================

1. Accept vendor contracts through a Streamlit web interface.
2. Extract text and metadata from PDF, DOCX, and optionally TXT files.
3. Detect and redact approved categories of Personally Identifiable Information using Microsoft Presidio and spaCy.
4. Split sanitized contracts into meaningful clause-based chunks while preserving page and source metadata.
5. Generate 384-dimensional embeddings locally using granite-embedding:30m through Ollama.
6. Store and retrieve contract chunks using a persistent ChromaDB vector store.
7. Query the vector store using enterprise compliance requirements.
8. Use a local Ollama model to compare retrieved clauses with explicit policy rules.
9. Classify each requirement as COMPLIANT, NON_COMPLIANT, AMBIGUOUS, MISSING, or REVIEW_REQUIRED.
10. Return evidence-backed findings with citations and remediation recommendations.
11. Store audit runs, findings, feedback, model versions, and prompt versions.
12. Evaluate retrieval and generation quality using automated tests and RAG metrics.
13. Package the system for repeatable execution using Docker.
14. Keep human review mandatory for high-risk or uncertain findings.

============================================================

Document Processing:
- pypdf and PyMuPDF for PDFs
- python-docx for DOCX files
- Preserve filename, page number, clause heading, and chunk identifier
- Reject encrypted, unsupported, malformed, empty, or oversized files with controlled errors

PII Redaction:
- Microsoft Presidio Analyzer and Anonymizer
- spaCy model: en_core_web_lg
- Use an approved entity allow-list rather than every Presidio entity
- Initial entity list: PERSON, EMAIL_ADDRESS, PHONE_NUMBER, IP_ADDRESS, LOCATION, URL, CREDIT_CARD, and IBAN_CODE
- Add custom recognizers later for internal IDs, account IDs, contract references, hostnames, and customer identifiers

Embedding Model:
- Provider: local Ollama runtime
- Model: granite-embedding:30m
- Verified output dimension: 384
- Use the same exact embedding model and version for document indexing and query generation
- Record the model name, tag/digest, license, and security approval

Vector Store:
- ChromaDB PersistentClient for development and a single-instance demonstration
- Persist original sanitized text, policy-safe metadata, source file ID, page, clause, and chunk ID
- Use collection versioning when the chunking strategy or embedding model changes

Inference Engine:
- Ollama local runtime
- Preferred model: granite4.1:8b for a 16 GB RAM VM
- Smaller fallback: granite4.1:3b
- Temperature: 0 or another low deterministic setting
- The LLM compares retrieved evidence with an explicit policy rule
- The LLM must not invent policy thresholds
- Require structured JSON and validate it with Pydantic

Persistence:
- SQLite for a local single-instance demonstration
- SQLAlchemy and Alembic for data access and migrations
- PostgreSQL recommended for multi-user or multi-instance production deployment

Evaluation:
- Ragas for selected RAG metrics
- PyTest, pytest-asyncio, and pytest-cov
- Ground-truth synthetic contracts must include compliant, non-compliant, ambiguous, and missing cases

Monitoring:
- Structured logging with structlog
- Prometheus-compatible metrics
- Health endpoints for the API, ChromaDB, database, Ollama, and model availability

18. PRODUCTION SECURITY REQUIREMENTS
============================================================

- Local-first or approved internal inference only
- No original contract text sent to unauthorized external APIs
- Validate file extension, MIME type, and file signature
- Enforce maximum upload size and processing timeout
- Scan uploads for malware in production
- Sanitize filenames and isolate user files
- Encrypt data in transit and at rest
- Apply authentication, authorization, and per-user access controls
- Redact PII from logs and telemetry
- Define contract, vector, audit, and report retention periods
- Support secure deletion
- Use least privilege for services and storage
- Protect against prompt injection embedded in contracts
- Treat contract text as untrusted data, never as system instructions
- Require citations for every model-generated finding
- Require human review for high severity, ambiguous, missing, conflicting, or low-confidence findings
- Track model name, model digest/version, prompt version, policy version, and code version
- Back up audit records and test restoration procedures
- Use dependency, container, and vulnerability scanning
- Pin production container images, models, and dependencies by version and digest/hash

============================================================

Minimum functional acceptance:
- Supported files extract correctly
- PII is redacted before embedding and inference
- Ollama granite-embedding:30m returns 384-dimensional embeddings
- ChromaDB data persists across restarts

- Retrieval tests use ground-truth expected clauses
- No fabricated citations
- No compliance decision from irrelevant context
- Missing evidence is not presented as proof
- Prompt injection text does not override application instructions
- Repeat runs at temperature 0 are sufficiently stable
- Quality thresholds are defined from measured evaluation results, not guessed

Minimum operational acceptance:
- FastAPI health endpoint works
- Streamlit can call the backend
- Ollama unavailability causes a controlled error
- ChromaDB or database failures do not corrupt an audit silently
- Logs contain trace IDs but no raw PII
- Docker deployment uses persistent volumes
- CI/CD blocks release when tests or security checks fail

============================================================
20. IMPORTANT DESIGN DECISIONS
============================================================

- Retrieval and evidence are more important than fluent generation.
- Presidio redaction occurs before embeddings and LLM calls.
- The policy engine supplies explicit requirements and thresholds.
- The LLM performs evidence-grounded comparison and explanation.
- Pydantic validates all model output.
- ChromaDB stores sanitized text only.
- Original documents are retained only according to an approved policy.
- Local Ollama inference is preferred for privacy.
- Synthetic data is used for development and evaluation.
- Human reviewers remain responsible for final legal/compliance decisions.
- The system is a decision-support and audit-assistance tool, not autonomous legal advice.
